## 角色与职能

- `测试`：设计用例，阐述某个用例是要测哪些需求的哪些功能，以及测试步骤的目的（为什么是这么操作）
- `需求方`：需求的唯一标准。评判开发实现（弱关心，除非发现重大缺陷）、测试用例（主要是功能表现）是否满足需求要求
- `开发`：从代码实现的角度看测试用例是否正确。同时检视这个测试点是否存在步骤不合理、观察点遗漏的情况（根据重要性、必要性、受益、复杂度等多维度评估后来补充，不是对所有的代码分支做覆盖）
- `故障模式库`：根据历史缺陷分析出来的最容易出问题的点和对应的触发场景

### 测试（必须）

输入：
- 需求文档.md
- 故障模式库(暂无)
- 改进建议、要求
- 历史功能
- 用例列表

输出：
- 用例列表

### TSE

需要更多经验和故障模式输入，不仅针对本次任务，是一个更泛用的角色（输入有限的时候不涉及）

### 需求（必须）

输入：
- 需求文档.md
- 用例列表

输出：
- 改进建议

### 开发（有代码支撑的时候才有意义）

输入：
- 业务代码
- 用例列表

输出：
- 改进建议

## workflow

1. 需求分析（需求文档承载），开发和测试线下参与
2. 系统设计&评审（与代码实现合并），应有但是无测试&需求方参与
3. 软件设计&评审（与代码实现合并），应有但是无测试&需求方参与
4. 代码实现
5. 测试设计，开发和需求方不参与
6. 测试设计评审，应有但是无开发&需求方参与

环节 `1` `2` `3` `4` 测试不参与，workflow 着重完成测试设计和评审环节

### 流程

测试输出用例 -> 是否还存在 drafted 状态的用例 -> 开发评审(暂无q) -> 需求方评审 -> 测试输出用例(此次只是修改)
           -> 否 结束任务

### Node

1. 测试输出用例使用 2 个 Node
    - Node1 读取需求文档、故障模式库，输出初版的测试用例
    - Node2 根据评审反馈的结果修改测试用例，提交复审
2. 需求方评审使用 1 个 Node
3. 判断结束使用一个 no-agent 的 Node

#### 测试节点1

读取需求文档，输出第一版用例，只存储 drafted 状态的。

#### 测试节点2

修改审核过后的测试用例，只做修改不补充，只访问 drafted

#### 开发节点

skip

#### 需求

可以访问 drafted、reviewed、deprecated
可以补充可能遗漏的测试用例

### 状态设计

需要跨节点追踪的状态：
- drafted、reviewed、deprecated 状态的 testcase
- 或许还需要检查标志位看看是否需要 break
